# modern agent

把「agent」这个词的外壳剥掉，剩下的大概是一句话：==让模型自己决定下一步做什么，并且真的去做==。单轮 chat completion 是「问一句、答一句」，agent 是「给个目标、它自己跑若干轮」。差别不在模型多大，而在于控制流从调用方转移到了模型手里。

这篇笔记按我自己拆解的顺序写：最小闭环、循环怎么退化、上下文为什么是真正的瓶颈、工具怎么设计、多 agent 什么时候值得、最后怎么判断它到底行不行。

## 一、最小闭环：模型 + 工具 + 循环

一个能跑的最小 agent 只需要三样东西。

1. **一组工具描述**，通常是 JSON Schema，告诉模型有哪些函数、参数是什么。
2. **一次带工具定义的模型调用**，模型返回的不再是纯文本，而可能是 `tool_calls`。
3. **一个执行器**，把工具真正跑起来，把结果作为一条 `tool` 消息塞回对话，再调一次模型。循环到模型不再要工具为止。

用伪代码写就是这样：

```text
messages = [system, user]
loop (max 20):
  resp = model(messages, tools)
  if resp.tool_calls is empty: return resp.content
  for call in resp.tool_calls:
    result = execute(call.name, call.args)
    messages.append(tool_result(call.id, result))
```

就这么多。剩下的复杂度全部来自三个地方：模型选错工具、工具返回太多或太少、以及循环跑长了以后上下文塞满。

举个具体例子。你让它「查一下上个季度上海的订单为什么掉了」，它需要的不是一次搜索，而是：先调 `list_regions` 确认区域标识，再调 `query_metrics(region=shanghai, quarter=2026Q3)`，发现是退款率异常，再调 `query_refunds` 按 SKU 拆分。整个过程四到六步，每一步的输入都依赖上一步的输出。==这种「下一步取决于上一步结果」的链式依赖，才是 agent 和 workflow 的分界线==：如果流程完全固定，写死就行，不需要 agent。

## 二、循环会怎么退化

最常见的心智模型是 ReAct 那套：思考、行动、观察，再来一轮。它确实好用，但工程上要准备好它退化的几种方式。

**过早收敛。** 模型看到第一个像样的结果就宣布完成。比如让它核对一份配置，它读了一个文件就说「已经配置正确」，而实际上还有两个环境文件没看。缓解办法是要求它在结束前显式列一份「已核对清单」，或者干脆把验收条件写进 system prompt：必须覆盖哪些文件、必须给出哪些证据。

**重复调用。** 参数几乎不变地反复调同一个工具，尤其是在工具返回空结果时。这通常意味着工具的错误信息没有区分「没查到」和「查错了」，模型只能靠重试。

**编造工具名。** 工具一多就容易出现幻觉调用，比如把 `read_file` 叫成 `file_read`。这类错误应该在执行器里直接返回一条可读的 `unknown tool, available: [...]`，而不是抛异常中断循环。

**无限循环。** 必须有硬上限，比如 20 到 30 轮，超了就把当前状态和未完成的部分交回去。上限不是能力问题，是账单问题。

## 三、上下文才是真正的瓶颈

新手容易把上下文窗口当成内存，觉得塞得下就行。实际上它是==工作台面==：台面越大越乱，模型越容易在中段丢东西。agent 的稳定性提升，八成来自上下文管理，而不是换更强的模型。

实践中我会把它分成三层：

| 层 | 放什么 | 生命周期 |
| --- | --- | --- |
| 工作记忆 | 当前任务的对话、scratchpad、最近几次工具结果 | 单次任务 |
| 情景记忆 | 历史会话、任务记录、可检索的日志 | 跨任务，按需检索 |
| 语义记忆 | 规则、项目约定、领域知识 | 长期，常驻或按路径加载 |

关键手法有三个。

**外部化。** 中间结果不要留在对话里，写进文件。分析一份 5 万行的日志，正确做法是跑一个脚本把统计结果写进 `report.md`，然后只把文件路径和摘要带回上下文。这样即使跑五十轮，上下文也只增长几行。

**压缩。** 长任务到一定轮次做一次摘要，把「已经确认的事实」和「还没做的事」分别列出来，丢掉过程。压缩要有损，但不能丢结论，否则模型会重新走一遍弯路。

**预加载的边界。** 常驻的规则文件（项目约定、风格指南）要短。一份 800 行的约定文件放进去，实际被遵守的通常是开头和结尾各 50 行。要么精简，要么改成按需读取。

## 四、工具设计比 prompt 更重要

很多「模型不听话」的问题，本质是工具接口设计得不好。几条经验：

- **粒度对齐任务，而不是对齐 API。** 与其暴露 `get_user`、`get_orders`、`join`，不如直接给 `get_user_orders(user_id, limit)`。一次调用能干完的事，不要逼模型编排三次。
- **返回值要裁剪。** 搜索工具返回 100 条原始记录，模型只会看前几条，剩下的全是噪音和 token。返回 top 5 加一句「共 87 条，已按相关度截断」。
- **错误信息要可行动。** 不要只返回 `error: 400`。返回 `参数 region 必须是以下之一: shanghai, beijing, shenzhen`，模型下一轮就能自我修正。
- **写操作要幂等或可回滚。** agent 重试是常态。发邮件、下单、删文件这类动作，要么带幂等键，要么先产出「计划」等确认。
- **描述里写清楚什么时候不要用。** 比如「不要用这个工具读超过 10MB 的文件，用 `tail_log`」。负面约束往往比正面描述有效。

## 五、多 agent：什么时候值得拆

多 agent 现在有点被滥用了。判断标准其实很朴素：==拆分能不能带来上下文隔离、并行收益，或者权限边界==。三条都不占，就别拆。

**值得拆的场景。** 一个调研任务要读 20 个网页，每个网页内容都很长。让主 agent 串行读，上下文会被塞爆；派 4 个子 agent 各读 5 个，只回传结构化摘要，主 agent 的上下文干净得多。这是上下文隔离带来的收益。

**也值得拆的场景。** 代码审查里，「安全」「性能」「可维护性」三个视角并行跑，互不干扰，最后汇总。这是并行收益。

**不值得拆的场景。** 一个三步就能做完的线性任务，硬拆成 planner、executor、reviewer，结果多了两次序列化和一次信息丢失，成功率反而下降。子 agent 之间靠自然语言传话，是==有损压缩==，每传一次就掉一点细节。

编排形态上常见三种：supervisor 模式，一个主 agent 分派和汇总；pipeline 模式，固定顺序流水线，每段可以是一个 agent；handoff 模式，把控制权连同上下文一起交给下一个。前两种好调试，第三种灵活但难追踪。

## 六、怎么判断它行不行

不要靠感觉。至少看四个数：

1. **端到端成功率**：给定 50 个真实任务，完整做对几个。这是唯一对用户有意义的指标。
2. **单步工具正确率**：工具名、参数、参数类型分别对不对。端到端失败往往能定位到某一步。
3. **平均轮次与 token 成本**：同样的任务，轮次从 8 降到 5 通常是上下文管理起效了。
4. **失败类型分布**：是找不到信息、用错工具，还是做对了但没交付。三类失败的修法完全不同。

配套的是 trace。每一步的输入、模型输出、工具返回、耗时都要留。没有 trace 的 agent 调试基本靠猜，而 agent 的失败又高度非线性，改一个 prompt 经常修好 A 弄坏 B。

## 七、一个能落地的最小架构

如果明天要从零写一个，我会按这个顺序：

- 先写工具层，每个工具单独可测，错误信息人工审一遍。
- 再写循环，带轮次上限、超时、以及「达到上限时如何优雅退出」。
- 上下文按需加载：常驻只放一段短的规则，其余走文件读取或检索。
- 中间产物一律落盘，对话里只留路径和摘要。
- 写操作先出计划，确认后执行。
- 最后才是加多 agent，而且只在确实撞到上下文或并行的墙时才加。

这套东西不新，也没有哪一环需要多聪明的模型。真正拉开差距的是第二到第四节：循环的边界条件、上下文的取舍、工具接口的手感。这三样做扎实了，换哪个模型都能跑；做不扎实，模型再强也只是把错误犯得更快。
